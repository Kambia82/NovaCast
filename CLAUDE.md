# NovaCast — Working Notes for Claude

**Read `NOVACAST_BLUEPRINT.md` first.** It is the product source of truth (direction, architecture guardrails, feature roadmap, priority order). This file is the condensed version plus a live status snapshot — update the status section as work lands, but resolve any conflict in favor of the blueprint, not this summary.

## Non-negotiable guardrails

- Firebase/Firestore is the backend. **Never** reintroduce Supabase — no `@supabase/supabase-js`, no `supabase.from(...)` calls, no Supabase env vars, no Supabase tables as a fallback. (`lib/supabase.ts` is unused dead code left in place; do not build on it.)
- Don't redesign NovaCast into a new concept, collapse it back into a single-flow wizard, remove existing menus/flows, or migrate architecture — unless explicitly instructed.
- Don't force accounts, catch logging, or history on users. Every advanced capability (login, voice coach, catch log, tackle analytics) must stay optional; the "open app → find water → fish → leave" path must keep working with zero setup.
- Don't build a social/community feed. NovaCast answers "what should I do right now," not Fishbrain.
- Don't pre-decide monetization. No feature gating without real user data (see blueprint §21-23).

## Development workflow (blueprint §25)

For any non-trivial change: **(1) inspect** what already exists (implemented/partial/broken/missing, existing components/services/data) → **(2) diagnose** in plain language before touching code (what's broken, what already solves part of it, smallest fix, files involved) → **(3) implement only the approved scope** → **(4) verify** with typecheck/build/tests, and say plainly when something (GPS, maps, live Firebase, weather/GIS APIs) can only be confirmed on a real device/deployment, not from a clean build.

## Entitlements / future monetization architecture (2026-09-04, blueprint §13–15)

Built per explicit instruction: **no paywall, no payments integration now** — every feature ships FREE and enabled today. The point is that a future decision to charge for something is a config edit, not a rewrite.

- `src/services/entitlements/` — `FeatureFlag` (`key`, `tier: 'free'|'premium'`, `enabled`) in a single `FEATURE_REGISTRY` (`featureFlags.ts`); `Entitlements` (`role: 'user'|'admin'|'owner'`, `plan: 'free'|'premium'`); `hasAccess(entitlements, featureKey)` is the *only* function anything should call — owner/admin always pass regardless of plan (§14), a disabled flag always denies, a free-tier flag always passes, a premium-tier flag needs `plan === 'premium'`. `getEntitlements(user)` resolves a signed-in user's `role`/`plan` from their Firebase ID token's custom claims (`services/auth.getAuthClaims()`) — guests resolve instantly to `{role:'user', plan:'free'}` with no network call.
- **No hardcoded admin secret for this system** (§14 explicit requirement) — `role`/`plan` are custom claims, settable only server-side via the Firebase Admin SDK (a script or Cloud Function with project-owner credentials), never client-writable. This is deliberately NOT implemented here (no server component exists yet) — assigning the first owner claim is an external, one-time ops task once a real Firebase project exists; documented, not fabricated. This is a *separate, new* system from the pre-existing hardcoded `#admin` panel in `App.tsx` (`adminPw === 'castmaster2025'`, gating curated-lake CRUD only) — that panel predates this work, is a different lower-stakes concern (content management, not premium-feature/role access), and was left alone this pass per "don't redesign unnecessarily"; it should eventually be migrated onto this same role system rather than kept as a second parallel mechanism.
- `hooks/useEntitlements.ts` — React hook (`{entitlements, can(feature)}`). Wired into one real call site as proof the plumbing works end-to-end: `NovaCastOnTheBank.tsx`'s voice controls check `can('ai_voice_coach')` (currently always true — voice ships free) instead of being unconditionally rendered, so moving voice behind PREMIUM later needs a one-line `featureFlags.ts` edit, not new UI code.
- Current registry (all `tier:'free'`, `enabled:true`): `lunar_advanced`, `barometric_advanced`, `ai_voice_coach`, `environmental_advanced`, `catch_analytics`, `expanded_intelligence` — chosen to match the blueprint's own list of potential future premium candidates.
- **Admin area (§15):** foundation only, no dashboard UI built (per explicit "prioritize secure architecture over a large UI"). The domains it would eventually manage (feature flags, content, recommendation config, starter-kit defs, retailer config, AI provider status, curated water, announcements, analytics, user admin) all already have a config surface it could read/write (`FEATURE_REGISTRY`, `data/reference.ts`, `data/recommendations.ts`, `services/starterKit/data.ts`, `services/retail/types.ts KNOWN_RETAILERS`, the existing `adminWaters` Firestore collection) — an admin UI would be a thin layer over these, not a rewrite, when/if built.

## Location error messaging (2026-09-02)

- Root cause of the long-standing "location permission denied even though it was enabled" report: **every** `getCurrentPosition` error callback in the app hard-coded a "permission denied" message and never inspected `GeolocationPositionError.code`. Codes 2 (POSITION_UNAVAILABLE — common on mobile / weak signal) and 3 (TIMEOUT) both fire that same callback, and opening the dev QR-code URL (`http://<lan-ip>`) is an insecure context where geolocation is unavailable — all three surfaced as "denied".
- Fix: new `src/lib/geo.ts` — `GEO_OPTS` (bounded `timeout: 15000`), `geoPreflightError()` (unsupported / insecure-context check to run *before* the spinner), `geoErrorMessage(err)` (code-specific: 1→blocked, 2→no fix/signal, 3→timed out, else generic), `getPosition()` promise wrapper. Applied at all 5 call sites: `App.tsx` `loadWeather` + `startOnTheBank`, `NovaCastRecon.enableLocation`, `NovaCastWizard` `findNearMe` + `loadWeather`. Behaviour otherwise unchanged; the "GPS failed" vs "no water found" distinction in Recon was already correct and is preserved.
- Not changed (pre-existing, out of scope): Wizard Step 6 `buildNearbyList` still searches only the curated `waters`/`adminWaters` DB, so a successful GPS fix with no curated match still shows "No known spots in our database" + a Google Maps link (blueprint §4 wants a real fallback here — Recon already does Overpass/3DHP, the Wizard does not).

- Environmental model: `services/lakeSnapshot/` — `buildLakeSnapshot({water, weatherApiKey})` → `LakeSnapshot`. Every field is a real value with a `source` or `available:false`. Astro/season from `lib/astro.ts` (computed, no API).
- Fishing intelligence: `services/ai/` — `getFishingIntelligence(ctx)` + `buildFishingContext(...)` + `spokenAnswers(insight)`. `FishingContext` = water/environment/conditions/observations/tackle/history/at. Provider-swappable (local rules engine ↔ hosted model via `VITE_AI_ENDPOINT`). Never import a provider directly.
- Voice: `lib/voice.ts` — `speak()`, `createRecognizer()`, `speechSupported`/`recognitionSupported`. Everything must work with neither.
- Auth + per-user data: `services/auth/` (+ `hooks/useAuth.ts`), `services/userData/` (`getUserDataStore(uid)`), `services/catchLog/` (`getCatchLogStore(uid)`). No uid ⇒ localStorage (guest, the default). `firebaseConfigured` false ⇒ auth is a no-op; guest experience is untouched.
- Entitlements / feature access: `services/entitlements/` (+ `hooks/useEntitlements.ts`) — `hasAccess(entitlements, featureKey)` only; never check `role`/`plan` inline in a component. Add a feature by adding one `FeatureFlag` to `featureFlags.ts`'s `FEATURE_REGISTRY` (`tier:'free'` today — flip to `'premium'` when a real decision is made, nothing else changes).
- Unit conversions: `lib/units.ts` (`hpaToInHg`) — reused by both the Lake Snapshot display and the AI context so they never disagree.
- Catch Log: `services/catchLog/` — take a `CatchLogStore` from `getCatchLogStore(uid)`. UI in `NovaCastCatchLog.tsx` (`store` prop).
- Retail / price preview: `services/retail/` — `getGearOffers(queries)` (merges every configured provider) / `listRetailers()` / `retailerCoverage()`. Add a retailer to `KNOWN_RETAILERS` first, then a priced `RetailProvider` in the `REGISTRY` when an API exists. No web scraping — official APIs or search links only. No fabricated prices; `relativeCost` only ranks prices that are already verified.
- Beginner Starter Kit: `services/starterKit/` — `generateStarterKit(criteria)` (NovaCast's own list, always available) vs `getPreassembledKits(criteria)` (real retailer bundles, `[]` until an API is configured). UI in `NovaCastStarterKit.tsx`, mounted inside the Shopping screen.
